# 单入口自动靠桶：接入与本轮实车结果

核心命题：用户只启动一个主入口，目标选择与各阶段切换由程序完成，不能依靠操作员手动提供框或逐段启动来声称自动流程已跑通。

## 入口

`deploy/run_mission.sh --out <本轮独立输出目录>` 启动总入口。它启动只读视觉子进程（NPU0），等待新帧，然后启动唯一串口控制器；控制器使用原 `TargetLock('auto')` 自动获取初始目标，再将该身份交给已有的持续追踪和恢复逻辑。后续沿用共享A/B调度、前进至A131–132、模型辅助测距（NPU2）和20cm附近停车。阶段交接不需要人工选择目标或另起脚本。

入口在 `/home/elf/deploy/bucket_approach_v2_candidate_20261125/deploy/run_mission.sh`，未修改开机服务，原纯机械臂追踪入口仍保留。冻结v1基线不变。当前入口要求已就绪且禁用的A73/B0/C0起始姿态；现有控制器会检查真实串口状态，不把普通启动当作重新上电，不重复登记零点。

总入口持有单实例锁，检查资源文件和端口；串口使用可配置的稳定by-id标识，消除旧USB插口by-path失效。自动锁桶前不发送运动。丢失后只验证原目标，不挑另一个高分框续跑。控制器和视觉由总入口管理，根目录STOP或信号传入正在运行的控制阶段，包括左移阶段；等待正常禁用确认，不强杀串口控制器。

速度仍8%，全轮前进累计预算上限120秒，任务总时长上限300秒。预算不会随重捕获重置，耗尽后不自动启用。C150mm与额外左移100mm仍按用户先前决定记录为等待位移测量的计划，不以计时冒充位移。此入口尚不等于完整自主投喂路线。

## 本轮证据

本机15项自动锁桶/目标保持/预算检查通过；RK3588上22项检查通过，包括模拟UART的A/B与底盘互锁、丢失恢复及故障停车。这些检查不等于本轮物理验收。

第一次旧验收入口在写串口前因写死的by-path不存在而失败，发送记录为空。随后读取当前by-id设备确认A73/B0/C0、禁用、零点有效、无故障、指令计数190，完成路径修复。

单入口实车记录：`outputs/full_flow_v2_20261125/automatic_01/`。

- 原自动选桶器在第25帧锁定白桶，框 `[126,466,426,700]`，没有人工种子输入。
- 真实串口回传A73→91、B0→69.8mm、C保持0。约9.2秒后发生通信故障：`system_fault=1`、`result=6`、串口接收错误计数0→15，电机故障0。
- 已发送的118个控制帧全部底盘速度为0；尚未进入前进、测距靠近阶段，不能评价这次底盘有无动力。
- 最后正常禁用命令得到确认：A91/B69.8/C0、state0、enabled=false、故障已解除、错误计数保留15。没有重启任务或清零机构继续动作。
- 故障时追踪仍有当前目标，identity1、recovery_count0；此次不是桶丢失导致停车。

固件 `93c31b1` 的 `Bluetooth.c` 将硬件UART错误、接收重新挂起失败、接收队列满统一归入 `rx_fault`，状态帧只给总次数。因此现有证据不能区分接线/供电干扰与接收处理问题，更不能直接认定低电池或发送过快。此次不是之前的HWT航向超时。

## 当前结论与下一步

已建立的是单入口自动选桶与A/B接入确实运行，故障停车也收到确认；本轮完整靠桶验收未通过。优先定位正常控制串口在机构运动期间发生的接收故障，之后使用同一总入口重新做完整验收，不重复已确认的轮子方向测试，不通过忽略错误或自动解除硬故障继续行驶。
