# 初始目标连续性修复

要回答的问题是：画面已经追踪到桶，为什么任务仍需长时间等待？

两次实车日志显示，首次选择很快完成，长等待发生在随后A转动导致的失锁恢复。完整验收轮第一次失锁277.41秒；新一轮在A73→90的约0.6秒转动后，原桶相对最后可信位置移动超过250像素且不再重叠。普通画面追踪可重新选择目标，任务要求保持原桶身份，其旧位置门槛（160像素及IoU0.15）阻挡了正确目标。实拍外观相关性约0.795，也未达到旧兜底路径的0.85近期外观要求。

修复让任务复用现有`TargetLock.verified_reappearance`，限定为已知外观，保留连续新帧、几何质量及检测确认。未知目标邻近回退被禁用，原任务身份保持1；错误外观、歧义目标及重复帧反例仍不能恢复。优先保留原追踪器的可信参考库。首次A对准通过共享`FollowPolicy`限至10指令度/秒，行驶后回到30。

实时检查还揭示了关键调度问题：快速候选建立后，继续执行旧全局特征搜索使每次处理耗时约0.5–0.66秒，超出原有0.12秒连续帧间隔要求。修复在快速候选待确认时直接等待下一新帧；失败后仍可进入原特征搜索兜底，没有扩大帧间隔或故障保护门槛。

验证：

- 同一组18张实拍图像（采集跨度0.568秒），原版未恢复，第一版改动在3帧后保留原身份恢复。离线回放不代表实时吞吐。
- 板端逐帧实时取图确认了调度修复：3帧、总墙钟耗时0.163秒恢复，候选帧跨度0.100秒；处理耗时分别0.062、0.023、0.060秒，完成时图像年龄0.089秒。画面同时存在高分柜体误检。该检查未打开串口、未发送机构或底盘指令。
- 全量376项检查中368通过、8项环境跳过；最终调度修正后的相关24项回归全部通过，包含错误目标、歧义、重复帧、UART故障、原身份恢复及完整任务收尾。
