# STM32 已开机时直接启动追踪

本次修复回答的问题是：STM32 已经停稳、零点有效，为什么追踪程序仍一直等待复位？现场实时回传为 A73/B0/C0、两轴已登记、禁用、无故障，视觉预热也已完成；阻塞来自上位机旧台账的 `tracking_state_uncertain:telemetry_timeout`。旧监测器只接受“新的复位特征”，没有接受“控制器已经准备好”的分支。

新增分支连续观察新鲜回传，要求两轴零点有效、当前位置 A73/B0/C0、禁用、无故障、航向有效，命令和串口错误计数稳定。取得证据后沿用现有零点，重新执行串口预检、视觉自检和原有 A0→160→73 自检，再从新画面开始自动追踪。该路径不发送零点登记命令，也不等待供新复位使用的 8 秒窗口。

台账分别记录“本次发送过零点登记”和“本次沿用实时有效零点”，保留旧阻塞原因。正常应用再次启动继续沿用已完成的状态。暂停、损坏台账、故障、不在初始位置、丢失零点等情况不由这个分支放行；单个进程中的失败自检不会反复自动扫动。

新复位仍走原有等待和一次登记流程。B/C 没有新增机械到位反馈，沿用登记不构成新的物理回零测量。

新增回归覆盖旧超时台账恢复、无复位且无登记的 A 自检、视觉未就绪阻止运动、零点丢失停止、用户暂停保持、再次启动不重复自检，以及缓冲旧帧和变化计数不能伪造稳定状态。

现场验证：两次启动均自动沿用实时零点并进入 A 自检，均未发送登记命令、未复位 STM32。第一次完成左右扫动，但返回途中在 A84°收到 `system_fault=3 / HWT_data`；小步回到73°并确认禁用后再试，第二次在左扫途中 A37°收到同一故障。两次均自动停止，B/C回传始终0。最终追踪未开启，识别进程继续运行。现有证据不能区分传感器接线、供电、接收或固件判定问题；下一步需要定位HWT失效的触发原因，不应放宽故障保护。

203项回归中的唯一初始错误是旧测试替身缺少新增等待时长属性，补齐后相关16项全部通过；最终覆盖197项通过、6项跳过。详见[实机与回归摘要](powered-startup-evidence-20261123.json)。
