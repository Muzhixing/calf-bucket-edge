# 本轮突然卡顿的定位

## 建立的认识

7379帧原生数据与Python追踪/串口日志对齐后，可以排除“本轮NPU推理慢帧导致约0.72秒停顿”这一解释。此次连续性问题至少包含两种机制：可见目标的外观误拒绝触发停机重获；上层读取/调度间隙触发串口超时停用。后者根因仍需分段观测，不能直接归因USB线、网络或CSRT。

本轮保持用户要求的停用状态。此次诊断只读取历史日志、图像，运行录像回放，没有打开相机或串口控制，没有恢复机构。

## 关键证据

| 层级 | 本轮证据 | 解释 |
|---|---|---|
| NPU检测 | 7379帧，中位14.04 ms，P99 16.84 ms，最大20.04 ms | 模型推理没有出现数百毫秒慢帧 |
| 相机与原生输出 | 相邻帧间隔P99 36.16 ms，最大99.92 ms；采集至原生发布中位19.47 ms | 存在少量相机不规则帧，但不解释0.72秒窗口 |
| 追踪 | 实时日志中位32.26 ms，P99 62.58 ms，最大521.23 ms；外观拒绝/CSRT附近有多次100–278 ms帧 | 平均帧率不能代表最慢帧；此耗时还包含等待画面和诊断存图，并非纯计算 |
| 外观拒绝 | 帧5755、5849、5904、5933时桶均可见且原生检测有框，追踪进入`target_appearance_lost`；分别约0.305、0.169、0.294、0.169秒后重新跟踪 | 这些停顿不是完全遮挡，属于外观误失锁造成的控制中断 |
| 串口保护 | 主机相邻读取记录间隔722.7 ms，触发700 ms门槛；随后读取到两帧积压状态，并收到禁用确认 | 超时保护实际生效；不能据此证明STM32这段时间没发回传 |

关键时间窗口为RK3588 monotonic约3726.45–3727.21秒：原生检测连续发布23帧，NPU中位13.65 ms、最大16.07 ms；Python上层未正常持续更新追踪与读取串口，随后停用。该现象不依赖电脑浏览器画面传输即可在板端日志中成立，浏览器或Wi-Fi不能单独解释机械臂停止跟随。没有浏览器端呈现时间戳，尚未量化显示端额外延迟。

UART错误累计始终61、系统与电机故障均0；独立接收复查恢复约250 ms周期。相机日志有12条损坏JPEG警告，不能将其等同于USB断连，也不能用它们解释所有停顿。

## 反例与未决解释

对原录像1347帧进行板端纯视觉回放，开启CSRT时追踪计算中位13.57 ms、P99 46.61 ms、最大218.23 ms；独立10 ms心跳线程未出现超过40 ms的间隔。因此已复现外观恢复的计算长帧，但没有复现0.72秒上层共同间隙，不能直接写成“CSRT占住Python导致串口超时”。回放未包含实时相机、原生NPU并发、网页与大量图像落盘，线程调度、同步日志锁和I/O等待仍是待检验解释。

同一1347帧顺序回放关闭CSRT后，追踪计算中位13.85 ms、P99 42.29 ms、最大62.48 ms，超过100 ms的帧从9降为0；逐帧目标框和追踪状态完全一致，两者均1298帧有目标、49帧无目标，独立心跳均无超过40 ms间隔。这段录像中CSRT回退没有提供成功接受的额外定位，却增加了最慢帧耗时。它支持将CSRT移出同步关键路径，而不是笼统增加CPU/NPU负载。该配对回放不等于全部历史片段；原实机日志另有2帧通过CSRT接受，不能据此宣称CSRT始终无用。完整配对结果与逐帧一致性见`diagnosis_comparison.json`。

当前代码在多个线程共用日志锁下同步打开/追加文件；串口接收时间在日志写入之前记录，超时在返回后检查。这是需要测量的等待路径，不是已证实根因。后续应分别记录串口轮询开始/结束、循环间隔、日志锁等待/写入时间、各视觉阶段时间，必要时使用独立接收进程作为对照。不能仅放宽700 ms超时阈值来掩盖卡顿。

## 下一项最有价值工作

先用同段录像与无动作运行分离重获长帧和控制调度阻塞：给昂贵外观/CSRT补偿设置时间预算，让新的强检测关联尽早提供可信目标；把串口接收和控制时序与视觉计算、同步落盘隔离，同时保留完全遮挡暂停、中心容差保持和通信故障停用。重新启动机构需等待用户明确恢复测试。
