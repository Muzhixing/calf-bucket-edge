# 网页视频帧率与积压修复

## 结论与实机证据

在同一 RK3588、相机与 SSH 转发链路上，网页流畅预览从约 3.4 fps 提升到实测 21–25 fps。板端采集、检测与追踪处理维持约 30 fps。该对比评估流式传输、缓冲策略与流畅预览配置的组合效果。

| 观察对象 | 实测 |
| --- | --- |
| 原网页逐帧请求 | 20 次连续请求约 3.39 fps，响应耗时中位数 288.65 ms，JPEG 约 20.68 KB |
| 原全尺寸 MJPEG | 约 3.70 fps，JPEG 约 79.92 KB |
| 新流畅模式浏览器 | AX 与截图观察 21.0、25.1、23.9 fps，预览 480×270 |
| 新清晰模式浏览器 | 约 12–13 fps，预览 640×360 |
| 新流畅 JPEG | 保存的实机样本 8.87 KB |
| 视频反馈网络往返 | 12 次测量中位数 135.94 ms；存在约 200 ms 的波动 |
| 板端视觉处理 | 保存状态约 29.9–30 fps；追踪输入仍为 1280×720 |

现有链路带宽和时延仍会影响显示帧率。表中数值来自本次现场场景，不宣称任意网络均可达到固定 30 fps。帧龄字段表示板端采集到发送前的时间；浏览器另外计入本机排队与解码时间，不把该字段当作相机到显示器的完整时延。

## 机制与设计

旧页面每次等待 JPEG 请求和解码结束后才请求下一帧，并设置约 15 fps 的调度上限。一次网络往返约数百毫秒时，串行请求无法跟上板端 30 fps。全分辨率 MJPEG又明显增加了传输量。

`runtime/video.py` 独立承接视频输出：

- `GET /stream.mjpg?remote=1&profile=smooth|clear&client=<id>` 使用标准 multipart MJPEG 持续连接，消除逐帧请求的往返等待。
- 每帧携带序号、JPEG 长度及板端帧龄；发布 JPEG 与序号的原子性保持。等待客户端释放窗口后重新读取最新画面，拒绝发送已经过期的采集帧。
- 新网页通过 `GET /video-ack?client=<id>&frame=<id>` 确认已显示的画面。每个观看者最多 10 个未确认帧，限制包含代理缓存的在途数量；无反馈时断开重连。该反馈只管理网页视频窗口，与电机命令和串口停止 ACK 无关。
- TCP_NODELAY、合并帧头与 JPEG 的一次写入、小型发送缓冲及关闭代理缓冲提示减少小包等待和积压。最多保留 16 个带反馈的观看者，连接退出释放记录。

`runtime/video_stream.js` 负责分块解析和有界解码，不发送控制命令。解析器正确处理帧头/JPEG跨网络块、多个完整帧合并到一个块的情况。短时合包保留多帧供显示，解码器最多保留 3 个待处理帧；持续过载时保留较新的画面。解码完成后按浏览器绘制时机替换图片，失败和断线后重连；切换预览质量时旧连接的异步结果不会覆盖新画面。

默认流畅预览为 480×270、JPEG质量25；清晰预览沿用640×360、质量60。完整1280×720 JPEG、原始快照、框选坐标、检测和追踪输入保持。无需引入新前端框架或运行时依赖，JS随wheel和清单发布。

## 控制边界与验证

- 最终视频、预览与故障外壳相关 30 项 Python 检查通过，Node检查包含任意分块位置、网络合包、错误长度、有界解码、解码恢复等；追加检查确认相机未出首帧时，失联观看者仍会过期，避免重连占满窗口。
- 新视频反馈窗口检查覆盖上限阻塞、未来序号不能提前释放窗口、确认后仅移除已消费帧。HTTP检查确认不发送过期或重复帧，停止后流连接退出。
- 静态检查、格式检查及包含新 JS 的 wheel 构建通过。浏览器实测完成流畅→清晰→流畅切换及持续画面显示。
- 独立视频分支基于已发布main，主体改动的完整回归355项无失败，8项按环境跳过（6项可选CSRT、2项Linux PTY环境用例）；末次空闲连接清理修正通过上述30项针对检查。
- `Application`、所有机构/底盘/任务控制模块均未修改。Session除初始化预览字段与JPEG预览编码外，19个方法的AST与原版本逐项相同；原控制API请求、框选前停止、heartbeat和停止确认保持。

源码修复从已发布main单独建立分支，避免纳入尚未发布的任务提交。现场原来运行0.3.3行进候选，视频候选保留其原生程序、模型、标定及任务功能；先确认原任务完成，再按用户选择以`--observe-only`启动，仅预览、等待后续操作，没有重新执行任务。

现场候选中与本次视频无关的既有架构边界问题，单独记录在本地验证目录的`followups.md`与`baseline-architecture-failure.json`，视频分支没有修改对应控制模块。
