# 故障隔离与降级运行

核心约定：设备缺失只影响依赖它的能力。网页和状态服务先启动；有相机而无电机时仍显示画面和可用的检测。通信或控制故障解除后，需要操作者明确恢复运动。

采用现有分层模块内的故障隔离、能力依赖和生命周期管理，不引入新的追踪算法或额外服务框架。

## 维护入口

| 文件 | 唯一职责 |
| --- | --- |
| `src/bucket_robot/runtime/application.py` | `track`/`mission`共同外壳；先提供HTTP，再后台初始化；组织工作线程和进程 |
| `runtime/health.py` | 组件状态、新鲜度、能力依赖、运动故障锁存 |
| `runtime/http.py` | 页面、状态、视频和带令牌的控制API；不直接加载OpenCV或操作电机 |
| `runtime/supervision.py` | 视觉进程的超时、退避、重启 |
| `runtime/telemetry_monitor.py` | 无写入路径的串口观察；读取任务阶段的有效回传日志 |
| `runtime/raw_camera.py` | 原生后端不可用时的独立原始画面进程；没有控制路径 |
| `runtime/stationary.py` | 原有视觉会话与机构执行；消费健康状态，不复制能力判断 |
| `missions/coordinator.py` | 构造已有行进任务参数；生命周期统一交给应用外壳 |
| `deploy/vision_cpp/worker_channel.hpp` | 独立推理子进程的单请求IPC、异常和退出处理 |
| `deploy/vision_cpp/detector_process.hpp` | RKNN检测适配；保留已有模型、预处理、解码及候选框算法 |

静止追踪和行进任务继续共用`TrackingController`、目标会话与串口事务。新增任务消费已有组件，不能拷贝这些实现。

## 故障行为

| 情况 | 页面和视觉 | 控制与恢复 |
| --- | --- | --- |
| 无STM32/串口 | 保留画面与可用检测，显示通信不可用 | A/B/C、四轮状态无法确认；自动重连，不自动续跑 |
| 控制器报告机构故障 | 保留视觉并展示故障 | 锁存运动；处理原因后明确恢复 |
| 模型缺失、加载/推理失败或推理进程崩溃 | 视频继续，检测标为不可用；子进程退避重试 | 禁止依赖检测的运动；恢复检测不解除运动锁存 |
| 标定缺失或校验失败 | 原始画面；禁止把未校正图像用于定位 | 检测/追踪/运动能力关闭，修复后重新检查 |
| 摄像头断开 | 网页常驻，旧帧过期后不再提供 | 后台恢复；运动暂停 |
| 原生后端不能启动 | 状态服务继续；尝试原始画面后端 | 不能提供检测时禁用相关能力；周期性重新尝试原生后端 |
| 机构配置、响应参数或启动账本无效 | 保留画面与独立视觉功能 | 机构控制不可用，不能用默认机构范围代替无效配置 |
| 日志不可写/异步写入失败 | 界面和画面继续 | 禁止或暂停运动，避免无记录执行 |
| 停止未确认 | 明确显示“停止未确认” | 服务端拒绝恢复和重新初始化；不将进程退出当成禁用确认 |

当前协议只有控制器级故障、位置和有效性回传，没有A/B/C及四轮各自的在线位。因此页面不能准确声称“缺少某一台电机”；先显示实际可证明的状态。将来增加协议在线位后，在同一个健康注册表中细化即可。

## 状态和接口

组件状态包括`unknown`、`starting`、`ready`、`degraded`、`unavailable`、`stale`、`recovering`。每个组件只有一条当前记录，包含故障码、说明、首次/最近观察时间、重复次数、恢复方式和有效期。重复错误更新同一记录，不产生无限堆叠的弹窗。

`GET /health`表示状态服务存活，返回200；`GET /ready`按画面能力返回200或503；`GET /status`保留原有字段并增加`health.components`、`health.capabilities`、`health.motion_latch`。这些接口回答不同问题：服务在线不代表电机可用。

能力由依赖表推导。机构和行进能力还检查观察模式、日志状态和运动锁存。前端禁用按钮只是反馈；服务端检查和执行循环再次检查才负责阻止不满足条件的动作。

`POST /api/retry`停止并释放现有组件后重新检查，保持运动锁存。`start`和启动确认动作只有在检查通过后才解除可恢复的锁存。`STOP_UNCONFIRMED`不能用这些动作解除。控制API继续使用会话令牌并拒绝跨站请求。

控制器回传有效期0.7秒；画面HTTP输出有效期0.4秒；状态页也隐藏过期机构位置。任务日志只接受最近0.7秒的回传，不能用重放旧记录维持“正常”。靠近阶段读取该阶段的日志，保留原串口所有权交接。

视觉进程无画面10秒后重启，重试退避0.5至8秒。原生启动连续失败时穿插原始画面后端，30秒后重新尝试原生后端。模型子进程初始化期限8秒，每帧等待80毫秒，未完成请求超过1秒重建子进程；迟到结果不绑定到新帧。上述预算是本轮实现值，板端负载验收后再决定是否调整。

## 异常处理边界

预期的缺设备、读写失败、资产不完整被转换为组件状态。工作线程异常由生命周期边界捕获并锁存运动；HTTP请求失败只影响该次请求。模型放在独立进程，隔离C/C++崩溃和阻塞，普通`try/except`无法覆盖这两类错误。

程序被外部终止、端口已被其他进程占用、系统断电或内核故障不属于能够保证继续运行的组件异常。不能用吞掉全部异常的方式声称服务健康。

## 本地验证

```sh
python -m unittest discover -s tests -t . -v
python -m unittest tests.test_resilience tests.test_native_worker tests.test_release -v
python -m build --wheel
```

故障测试使用合成图像、本机HTTP、PTY模拟串口及独立C++测试进程，不访问真实相机、NPU或电机。C++测试覆盖初始化异常、推理异常、崩溃、卡死、重启及退出时间。它验证IPC隔离，不等于完整RK3588程序的构建或实机验证。
